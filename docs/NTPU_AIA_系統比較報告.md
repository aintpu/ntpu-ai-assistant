# NTPU AIA 新舊系統與 AI4X MCP Core 規格比較

報告人：盧信廷　日期：2026-10-04

## 一、摘要

依照老師提供的 AI4X MCP Core 12 份規格書（Spec-Driven Development），為 NTPU AIA 聊天機器人
（aia.ntpu.ai）加上 MCP 資料層。原本機器人只能查「人工整理後 commit 進 repo 的資料」，
現在改成「排程自動抓官網 → 有版本紀錄的資料庫 → 唯讀 MCP 工具 → 機器人查詢」。**目前已全部上線。**

- **舊系統**：沒有使用 MCP 的 NTPU AIA。
- **新系統**：使用 MCP 的 NTPU AIA。MCP 位於 **https://aia.mcp.ntpu.ai/mcp**，28 個來源每天自動同步，
  目前收錄公告 6,777 則、常見問答 1,038 題、法規 865 筆、介紹頁 5 頁。
- 正式站的「最新公告」與「法規、常見問答」都已改從 MCP 查詢，答案下方顯示資料更新時間。
- 用正式模型做端到端評估（36 題）：**新系統答對 25 題、舊系統 19 題**；
  回應時間中位數 **9.1 秒 vs 32.0 秒**。
- 對照 AI4X 規格的驗收項目共 18 項：**17 項完成**，1 項因刻意的設計決定而部分完成（第三節）。

## 二、舊系統與新系統比較

| 項目 | 舊系統（沒有使用 MCP 的 NTPU AIA） | 新系統（使用 MCP 的 NTPU AIA） |
|---|---|---|
| 資料來源 | 人工爬蟲或整理後，把 Markdown、Excel commit 進 repo | 學校官網 API 每天自動抓取，加上人工整理檔（法規、14 個處室的 FAQ Excel） |
| 更新方式 | 改檔 → commit → 重建容器與向量索引 → 部署 | 官網資料自動同步（每個來源約 20 小時重抓一次）；人工檔一個指令轉檔並上傳，不必重新部署機器人 |
| 公告時效 | 停在最後一次 commit，常常過期 | 每天同步；回答附「資料更新時間」 |
| 涵蓋範圍 | 21 個單位 | 21 個單位、28 個來源 |
| 版本紀錄 | 只有 git 歷史，看不出單筆資料何時改過 | 每筆資料都有版本，內容改變時保存舊版 |
| 原始資料保存 | 沒有 | 每次抓取的原始回應存 R2，以 SHA-256 命名、不可覆寫 |
| 資料出處 | 部分資料有來源連結 | 每筆都附 provenance：來源、信任等級、版本、驗證時間、內容雜湊、官方連結 |
| 資料驗證 | 沒有 | schema 驗證，不合格的資料隔離、不寫入；不補造欄位 |
| 資料消失 | 直接刪檔 | 連續 3 次完整抓取都沒看到才標為 inactive，從不刪除 |
| 查詢方式 | 容器內 FAISS 語意搜尋＋BM25＋rerank | 機器人呼叫 MCP 的唯讀工具（公告、介紹頁、法規、常見問答各有 search／get，共 8 個） |
| 答對率（36 題） | 19 題（53%） | **25 題（69%）** |
| 回應時間中位數 | 32.0 秒 | **9.1 秒** |
| 故障時 | 容器掛掉就無法回答 | MCP 失敗或查無資料時，自動退回舊的本機索引；開關可一鍵切回舊系統 |
| 給其他 AI 使用 | 不行，資料鎖在機器人裡 | 可以，任何支援 MCP 的 AI（例如 Claude）都能連 `aia.mcp.ntpu.ai/mcp` 查詢 |
| 測試 | 後端單元測試 | 後端 158 個測試，加上 MCP 的 184 個測試（單元／整合／安全）、契約快照、標準題組、lint |
| 上線與還原 | 沒有正式紀錄 | 上線紀錄（commit、Worker 版本）、還原說明、維運手冊 |

### 架構

```text
【舊系統】
人工整理的 Markdown／Excel ──commit──▶ 容器（FAISS 索引）──▶ aia.ntpu.ai 聊天機器人

【新系統】
學校官網（new.ntpu.edu.tw、strapi API）         人工整理檔（法規全文、法規彙整表、14 份處室 FAQ Excel）
        │ 只抓登記過的網址                               │ 一個指令轉檔並上傳到 R2 manual/
        ▼                                               ▼
ntpu-aia-ingest（排程 Worker）
   ├─ 原始回應 → R2（SHA-256、不可覆寫）
   ├─ 解析 → 正規化 → schema 驗證（不合格就隔離）
   ├─ 比對雜湊：相同只更新驗證時間；不同則保存舊版、版本 +1
   └─ D1 資料庫
        ▼
ntpu-aia-mcp（唯讀 MCP Worker，aia.mcp.ntpu.ai）
   ├─ POST /mcp    8 個唯讀工具
   ├─ GET  /health 各來源最後成功時間
   └─ GET  /about  工具登記表與負責人
        ▼
aia.ntpu.ai 聊天機器人
   ├─ 最新公告：MCP
   ├─ 法規／常見問答：MCP（體育室、通識、語言中心、校長室維持本機）
   └─ MCP 失敗或查無資料時，自動退回舊的本機索引
```

## 三、新系統與 AI4X 規格的比較

| 規格 | 規格要求 | 新系統的做法 | 狀態 |
|---|---|---|---|
| 06 §4 | 擷取與查詢分離 | 抓取 Worker 與 MCP Worker 分開部署；MCP 只能讀資料庫、不能連外 | ✅ |
| 06 §6–8 | 來源登記、白名單、SSRF 防護、逾時／大小／content-type 限制 | 只抓 source registry 登記的網址；阻擋 IP、localhost、metadata 主機；有逾時與大小上限，不跟隨轉址 | ✅ |
| 06 §9 | 保存原始資料 | 原始回應存 R2，以 SHA-256 命名、不可覆寫 | ✅ |
| 06 §12–15 | schema 驗證、雜湊比對、版本紀錄 | Zod 驗證；內容相同只更新驗證時間，不同則保存舊版、版本 +1 | ✅ |
| 06 §5 | 每筆資料附 provenance | 都有附；人工整理檔沒有官方連結時 `sourceUrl` 為 null，不補造連結（ADR-0004） | 🟡 刻意決定 |
| 06 §22 | 排程、可重跑（冪等）、資料消失不刪除 | 正式環境 19 個來源第二輪抓取全部 0 筆新增、0 個新版本；連續 3 次沒看到才標 inactive | ✅ |
| 07 §5 | 工具回傳資料新鮮度 | 每次查詢回傳 `freshness`（各來源最後成功時間） | ✅ |
| 07 §10 | 工具登記表、公開 v1 政策 | 未登記的工具不會註冊；`/about` 公開登記表 | ✅ |
| 08 §2 | 唯讀、風險 R0、資料等級 L0、不需權限 | 8 個工具全部符合；測試也檢查查詢不會改動資料 | ✅ |
| 10 §4 | 標準題組，涵蓋 8 類 | 17 題：精確、探索、篩選、日期、模糊、不支援、惡意輸入、多主題 | ✅ |
| 10 §7 | 契約快照 | 工具名稱、說明、schema 一旦改變，測試就會失敗 | ✅ |
| 10 §10 | model-in-loop 評估 | 正式模型實際回答 36 題，由模型對照參考答案評分（第四節） | ✅ |
| 10 | lint、型別檢查、測試 | Biome＋tsc＋184 個測試 | ✅ |
| 11 §10 | 正式環境上線檢查 | 10 項全部通過；28 個來源都是最新狀態，0 筆隔離 | ✅ |
| 11 | 上線紀錄、還原說明 | `mcp/docs/releases/`（每次上線的 commit 與 Worker 版本）、`mcp/ROLLBACK.md`、維運手冊 | ✅ |
| 12 | ADR | ADR 0001–0007 | ✅ |
| 12 | 負責人、維運手冊、工具說明 | `mcp/docs/` 內的 ownership、runbook、tools | ✅ |
| 12 | 規格驗收清單 | `mcp/docs/acceptance.md`，每項附證據位置 | ✅ |

### 刻意偏離規格之處（皆有 ADR）

| ADR | 決定 | 理由 |
|---|---|---|
| 0001 | 所有資料共用一張 entities 表 | 4 種資料結構相近，新增來源不必改 schema |
| 0002 | 關鍵字比對，不用向量索引 | 規格建議先用 SQL 查詢；評估結果新系統反而比舊系統的語意搜尋好 |
| 0003 | 法規、FAQ 以人工整理檔收錄（`manual_verified`） | 學校沒有可抓取的 API |
| 0004 | 人工整理檔沒有官方連結時 `sourceUrl` 為 null | 不補造連結；只以文字標示來源名稱 |
| 0005 | 每次排程只跑一個來源 | Worker 執行時間上限 |
| 0006 | 跨處室公告逐筆記錄所屬單位 | 同一則公告會由多個處室刊登 |
| 0007 | `aia.mcp.ntpu.ai` 網域切換到新 MCP，原服務保留 | 出問題可快速切回 |

另外：學校 strapi API 只接受 GraphQL POST，所以抓取用 POST。查詢內容是程式固定產生的，外部無法指定。

## 四、評估結果

### 1. 端到端評估（規格 10 §10，model-in-loop）

題目從 17 個處室的真實資料挑選，再改寫成使用者的問法（共 36 題，其中 2 題應回答「查無」）。
同一批題目分別問「舊系統」與「新系統」，由模型對照參考資料評分：回答須與參考資料一致、不能編造。

| | 答對 | 比例 | 回應時間中位數 |
|---|---|---|---|
| 新系統（MCP） | **25 / 36** | **69%** | **9.1 秒** |
| 舊系統（FAISS 語意搜尋） | 19 / 36 | 53% | 32.0 秒 |

答錯的題目大多是回答多講了參考資料沒有的內容（例如問勞工事假，又補充了公務人員的規定）。
評分標準刻意嚴格，新舊系統用同一套標準。

另做了檢索層比對（只看有沒有找到正確文件）：新系統 34/36、舊系統 33/36。

### 2. 評估過程中發現並修正的問題

| 問題 | 原因 | 修正 |
|---|---|---|
| 「我想問校慶在何時」「學校電話幾號」「期中考是哪一週」等被擋下，回「沒有可安全回答的資料」 | 範圍判斷太嚴：判斷不出處室就一律擋下；模型把諮商、信箱等判成與校務無關 | 判斷不出處室時改為跨單位檢索；說明本校業務範圍 |
| 「北聯大」「信義會館」「行天宮急難救助」「全民國防教育法」被擋下 | 模型不知道這些是本校資料裡的名詞，誤判為外部機構 | 範圍判斷改以資料為依據：知識庫有標題含這個詞就不擋 |
| 接受提議「好幫我整理」後被擋下 | 系統把「請幫我整理大學…」整串當成外校名稱 | 外校名稱只認真正的校名；補常見外校簡稱並檢查前後文（避免「行**政大**樓」被當成政大） |
| 17 個中文字以上的關鍵字讓 MCP 回 `INTERNAL_ERROR` | Cloudflare D1 的 `LIKE` 樣式上限約 50 bytes | 改用 `instr()` 比對，沒有長度限制 |
| 教務處最新公告顯示 9/23，官網最新是 10/2 | 「公告」被當成篩選條件；日期存 UTC 少一天 | 移除通用詞篩選；換算台灣時間 |

範圍判斷用正式模型跑 75 題檢查：修正前 56 題本校問題有 12 題被誤擋；
修正後**應回答卻被擋 0/63、應擋卻放行 0/12**（應擋的包括台大、政大、天氣、餐廳、寫詩、比特幣等）。
檢查腳本保留在 `evaluate/scope_probe.py`，之後改判斷規則時可以重跑。

### 3. MCP 本身

- 契約快照：8 個工具的名稱、說明、schema 一旦改變，測試就會失敗。
- 標準題組 17 題，涵蓋規格要求的 8 類；每題都檢查 provenance、查無資料時的行為，以及查詢不會改動資料。
- 正式環境上線檢查 10 項全部通過；冪等驗證見第三節 06 §22。

## 五、已知限制

- 「用學校 VPN 有什麼要注意」：範圍判斷正確，但檢索沒有找到該筆 FAQ，新舊系統都一樣。
- 範圍判斷的模型偶爾對同一題給出不同結果；已加入例子說明，但無法完全保證一致。
- 行政單位法規彙整表多數處室只有 20 筆，受限於目前取得的資料。

## 六、負責人

Data owner、Technical owner、Security reviewer、Production operator 目前都由盧信廷擔任。
一人兼任所有角色時沒有第二人把關；之後若有協作者，會優先把 security reviewer 交給別人。
